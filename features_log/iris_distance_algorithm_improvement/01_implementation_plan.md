# 홍채 기반 거리 알고리즘 개선 구현 계획서

## 1. 개요
현재 눈-화면 거리(`eye_screen_distance_cm`)는 홍채 지름(px)과 핀홀 카메라 모델로 계산한 뒤, 결과에서 **임의 보정값 20cm를 빼서** 사용하고 있다 (`src/core/indicator_calculator.py` 314~332행).
이 값은 제출 일정에 맞추기 위한 임시 보정이므로, 이번 작업에서는 **줄자로 실측한 거리의 사진 데이터셋**과 **오차 측정 테스트 프로그램**을 만들고, 측정된 오차를 근거로 알고리즘을 고쳐 임의 오프셋을 없앤다.

### 범위
- 포함: 오차 측정 테스트 프로그램, 홍채 지름 계산 개선, 거리 계산식 개선(20cm 오프셋 제거), 관련 문서 갱신
- 제외: 카메라 FOV 보정 (사용자 경험상 가장 흔한 **60° 고정을 의도적으로 유지**), 신규 UI, 시간 필터/히스테리시스 등 요청하지 않은 개선

## 2. 현재 알고리즘 분석

### 2.1. 처리 흐름
1. `landmark_extractor.py` (491~527행): FaceMesh 홍채 인덱스 468~477의 점을 **정수 px 좌표**로 모은 뒤, x 좌표 기준으로 좌/우를 나누고, 각 그룹의 `중심점에서 각 점까지 평균 거리 × 2`를 지름으로 사용한다.
2. `indicator_calculator.py` (314~332행):
   - `f_px = 설정 해상도 폭 / (2 · tan(HFOV/2))`
   - `Z_cm = (iris_diameter_mm · f_px / 지름_px) / 10`
   - 양안 중 **최솟값** 선택 후 `- 20cm`

### 2.2. 오차 원인 가설
| ID | 가설 | 예상 오차 형태 | 근거 |
| :--- | :--- | :--- | :--- |
| H1 | **홍채 중심점(468, 473)이 지름 계산에 포함됨** | 곱셈형 (거리 약 1.25배 과대) | 5개 점 중 1개가 중심(거리 0)이라 평균 반지름이 `0.8r`로 줄어듦 → 지름 20% 과소 → 거리 25% 과대. 60cm에서 75cm로 계산되어 **약 15~20cm 과대**, 현재 `-20cm` 보정과 맞아떨어짐 |
| H2 | 픽셀 좌표 `int()` 절사 | 무작위 노이즈 (먼 거리일수록 커짐) | 홍채 지름이 10~25px 수준이라 1px 절사가 4~10% 오차 |
| H3 | 좌/우 분할을 x 좌표 기준으로 수행 | 간헐적 이상치 | 인덱스(468~472 / 473~477)로 이미 구분 가능한데 좌표로 다시 나눔 |
| H4 | 양안 중 최솟값 선택 | 가까운 쪽으로 치우친 편향 | 노이즈가 큰 쪽 눈이 선택되기 쉬움 |
| H5 | 설정 해상도 폭과 실제 프레임 폭 불일치 가능성 | 곱셈형 상수 오차 | 지름(px)은 실제 프레임 폭으로, `f_px`는 설정값으로 계산 |
| H6 | 덧셈형 `-20cm` 보정 | 거리에 따라 오차가 달라짐 | 핀홀 모델 오차는 곱셈형이므로 고정값 빼기는 특정 거리에서만 맞음 |

> 가설은 테스트 프로그램으로 **먼저 측정해서 확인**하고, 확인된 항목만 수정한다.

## 3. 주요 변경 사항

### A. 실측 데이터셋 수집 (사용자 수행)
- 저장 위치: `data_test/iris_distance/`
- 파일명 규칙: `d{실측거리cm 3자리}_{순번 2자리}.jpg` (예: `d060_03.jpg`)
- 촬영 프로토콜:
  - 거리: 30, 40, 50, 60, 70, 80cm (6단계 이상)
  - 거리별 5장 이상, 정면 응시, 눈 뜬 상태
  - 실측 기준: **카메라 렌즈 ~ 눈(각막) 평면**까지 수평 거리
  - 실제 감지에 쓰는 웹캠과 같은 해상도(설정값 `camera_resolution_width`)로 촬영
- 촬영 보조 스크립트 `scripts/iris_distance_capture.py` 제공: 웹캠 미리보기 → 실측 거리 입력 → 키 입력으로 규칙에 맞는 파일명으로 저장

### B. 오차 측정 테스트 프로그램 (`scripts/iris_distance_evaluation.py`)
- **운영 코드를 그대로 호출**해 측정한다 (`LandmarkExtractor` → `IndicatorCalculator`). 별도 재구현을 하지 않으므로 개선 전후 비교가 곧 실제 앱 동작 비교가 된다.
- 이미지별 출력 (CSV: `data_test/iris_distance/results/evaluation_{시간}.csv`):
  - 실측 거리, 계산 거리, 좌/우 홍채 지름(px), 프레임 해상도, 오차(cm), 오차율(%)
- 요약 출력:
  - 거리 단계별 평균 오차, 표준편차, MAE, 평균 오차율
  - 오차가 **덧셈형인지 곱셈형인지** 판별하기 위한 `계산 거리 vs 실측 거리` 선형 회귀 기울기/절편
  - 산점도 그래프 저장 (`evaluation_{시간}.png`, y=x 기준선 포함)
- 비교 모드: 홍채 지름 계산 방식 후보(기존 / 중심점 제외 / 가로 지름 / 세로 지름 / 가로·세로 중 큰 값)를 같은 데이터에 동시에 적용해 결과를 한 표로 비교

### C. 홍채 지름 계산 개선 (`src/core/landmark_extractor.py`)
- 중심점(468, 473) 제외, 외곽 4점(469~472, 474~477)만 사용 (H1)
- `int()` 절사 제거, 실수 px 좌표 사용 (H2)
- 인덱스 기반으로 좌/우 분리 (H3)
- 지름 산출 방식은 B의 비교 결과에서 오차가 가장 작은 방식으로 확정
- 지름 계산을 별도 메소드(`calculate_iris_diameter_px`)로 분리 (SRP)

### D. 거리 계산식 개선 (`src/core/indicator_calculator.py`)
- `- 20.0` 하드코딩 제거 (H6)
- 거리 계산을 별도 메소드(`calculate_iris_distance_cm`)로 분리
- 양안 결합 방식: 최솟값 → 평균(한쪽만 유효하면 그 값) (H4, B 결과로 확정)
- H5가 측정으로 확인되면 실제 프레임 폭을 `landmarks`로 전달해 `f_px` 계산에 사용
- C·D 적용 후에도 **일정한 비율 편향**이 남으면, 덧셈 오프셋이 아닌 곱셈형 보정 계수 `distance_correction_scale`을 `data/posture_definition_criteria.json`의 `eye_monitoring`에 추가 (기본값 1.0, 값은 B의 회귀 결과로 결정)
- `except Exception: pass` → 디버깅 가능한 `logger.debug` 로그로 교체

### E. 문서 갱신
- `.github/rules/operation/posture_system_summary.md`: 홍채 거리 산출 절 추가 (계산식, 보정 계수, 측정 방법)
- `.github/operation-implementation-checklist.md`: 관련 항목 반영

## 4. 알고리즘 상세 (개선 후 예상)
```text
d_h = |P469 - P471|,  d_v = |P470 - P472|          # 실수 px
d_iris = 선택된 방식(d_h, d_v)                    # B 결과로 확정
f_px = frame_width / (2 · tan(HFOV / 2))          # HFOV = 60° 유지
Z_eye_cm = iris_diameter_mm · f_px / d_iris / 10
Z_cm = mean(Z_left, Z_right) · distance_correction_scale
```

## 5. 구현 단계
1. **1단계**: `scripts/iris_distance_capture.py` 작성 → 사용자 실측 데이터셋 촬영
2. **2단계**: `scripts/iris_distance_evaluation.py` 작성 → **현재 알고리즘 기준선(Baseline) 오차 측정** (오프셋 적용/미적용 모두 기록)
3. **3단계**: 측정 결과로 H1~H6 확인 → 결과를 사용자에게 공유하고 수정 범위 확정
4. **4단계**: C(지름 계산), D(거리 계산) 수정 → 같은 데이터셋으로 재측정
5. **5단계**: 남은 비율 편향이 있으면 `distance_correction_scale` 결정 및 JSON 반영
6. **6단계**: 단위 테스트 및 문서 갱신

## 6. 검증 계획
- **정량 검증**: 같은 데이터셋에서 개선 전후 MAE/오차율 비교 (목표 기준은 아래 확인 필요 사항에서 확정)
- **거리 의존성**: 거리 단계별 오차가 일정한지(덧셈 오프셋 없이도 전 구간에서 맞는지) 확인
- **단위 테스트**: 합성 홍채 좌표(알려진 지름)로 `calculate_iris_diameter_px`, `calculate_iris_distance_cm` 검증
- **회귀 확인**: `eye_close_warning`, 거북목 워커의 거리 점수(`judge_workers.py` 124~129행), 감지 화면 거리 표시(`detection_screen.py` 267행)가 정상 동작하는지 확인

## 7. 확정 사항 (사용자 확인 완료)
1. **실측 기준점**: 눈(각막) ~ 카메라 렌즈 수평 거리
2. **목표 정확도**: 30~80cm 구간에서 MAE 3cm 이하 또는 평균 오차율 ±5% 이내
3. **촬영 방식**: 보조 캡처 스크립트(`scripts/iris_distance_capture.py`)로 새로 촬영
4. **안경 착용 여부**: 안경 착용/미착용을 모두 촬영해 오차를 비교한다.
   - 파일명에 조건 접미사 추가: `d{거리}_{순번}_{glasses|bare}.jpg` (예: `d060_03_glasses.jpg`)
   - 평가 프로그램은 조건별 MAE/오차율을 따로 출력한다.
   - 두 조건의 차이가 목표 정확도 이내이면 **구분 없이** 하나의 알고리즘/보정 계수를 사용한다.
   - 사용자 안경 도수가 충분히 높으므로, 이 사용자 데이터에서 차이가 작으면 다른 도수는 추가 검증하지 않는다.
